# 性能优化：用工具定位问题

目标：拿到一个「慢 / 卡 / 死 / 涨内存」的现场，能指出时间花在哪个线程、哪段代码、在等谁。优化手法放在定位之后。

## 从这里开始

第一周只做一件事：用 Android Studio 的 **System Trace**（底层是 Perfetto）抓住 `ANRSampleActivity`，在图上指出主线程被子线程的锁堵住。

过关标准：不看源码，只看 trace，能说出「主线程停在等锁，持锁的是那个 sleep 30 秒的子线程」。

本仓库对应代码：`app/src/main/java/com/example/guo/exception/anr/ANRSampleActivity.kt`。

`MainActivity.onWindowFocusChanged` 里注释掉的 `Debug.stopMethodTracing()` 是旧的 Traceview 路径。Method Trace 会改写方法耗时，留到后面确认 Java 热点时再用。第一张现场用 System Trace。

## 先会分类，再选工具

同一句「卡了」对应完全不同的图。先把现象归进下表，再开工具。

| 现象 | 判断线（练习用） | 第一工具 |
| --- | --- | --- |
| 滑动、动画掉帧 | 一帧预算 = 刷新周期。60Hz 约 16.6ms，90Hz 约 11.1ms，120Hz 约 8.3ms。超过预算即掉帧；单帧超过约 700ms 记为冻结帧 | System Trace |
| 点了没反应，弹出无响应 | 输入事件约 5s 内主线程没处理完。前台 Broadcast 约 10s，前台 Service 约 20s | System Trace，配合 `/data/anr/` 里的 traces |
| 打开慢 | 冷启动到首帧，体感上超过 1s 就要看；线上过慢冷启动常按数秒记 | `adb am start -W`，再抓启动 System Trace |
| 越用越卡、闪退、内存涨 | Java 堆、Native 堆、Graphics 分开看。泄漏看「退出页面后仍被谁引用」 | Memory Profiler 的 heap dump |
| 发热、掉电 | 后台 CPU、唤醒锁、定位、网络 | Energy Profiler，再落到 System Trace / 线程 |

固定流程，每次一样：

1. 用同一台机、同一条路径复现，记下操作和大概时长。
2. 归进上表。
3. 抓一段刚好盖住复现动作的 trace，控制在几秒到十几秒。
4. 先看主线程，再看它在等的那条线程。
5. 写下一句结论：谁、在什么函数、等了多久、等的是锁 / IO / binder / 自己的计算。
6. 只改这一处，用同一条路径再抓一次对比。

## 路线

按顺序做。每段的练习都在本仓库 `com.example.guo` 里完成，包名 `com.example.guo`。

### 0. 半天：主线程在干什么

学这些就够开工：

- 主线程跑一个消息队列。输入、绘制、生命周期都是往这个队列投消息。
- Choreographer 按 Vsync 编排一帧：输入、动画、measure/layout/draw，然后交给 RenderThread。
- 主线程在这一帧里做重活、等锁、读磁盘、同步 binder，这一帧就超预算。连续几秒不回来，输入 ANR。
- ANR 的栈是「超时那一刻」的采样，慢函数可能已经跑完。要看整段时间，用 trace。

练习：读一遍 `ANRSampleActivity.test1()` 的注释，用自己的话写出两条线程的时序。先不抓 trace。

### 1. 第 1 周：System Trace（起点）

工具：

- Android Studio：Profiler → CPU → System Trace。
- 或开发者选项里的 System Tracing，到 [ui.perfetto.dev](https://ui.perfetto.dev) 打开。
- 命令行留到后面，Studio 里能完成第 1 周。

看图顺序：

1. 找到本应用进程，展开主线程（通常带 `main` 或进程名）。
2. 看主线程上最长的一段 slice，点进去看名字。
3. 若是 `monitor contention` / `Lock`，点开看 owner 线程。
4. 切到 owner 线程，看它这段时间在 sleep、在跑，还是也在等别人。
5. 顺手看 `Binder`、`HeapTaskDaemon`（GC）、`RenderThread`。主线程空等时，原因经常在这三处。

练习 A，锁等待。运行 `ANRSampleActivity`，在进入页面前开始抓 System Trace，盖住 onCreate。预期：

- 子线程先进 `testANR()`，`@Synchronized` 拿到 `this`，`SystemClock.sleep(30s)`。
- 主线程 10ms 后进 `initView()`，同一把锁，停在等锁。
- 结论句应类似：主线程阻塞约 30s，等子线程释放 `ANRSampleActivity` 的实例锁。

练习 B，主线程自己空转。`MainActivity.onCreate` 末尾现在有一段 `while (true) continue`（未提交）。抓进入首页的 System Trace。预期：主线程上是密集运行，没有等锁。这和练习 A 是两种图，都叫 ANR，修法不同。

两张图并排写三行笔记：主线程状态、对端线程、第一嫌疑代码。

### 2. 第 2 周：掉帧

在练习 A 的看图顺序上，加一帧的标记：

- `Choreographer#doFrame` 的时长是否超过刷新周期。
- doFrame 里面是 measure/layout、draw，还是业务代码。
- `RenderThread` 是否更长。主线程短、RenderThread 长，多半是过度绘制或复杂渲染，先别改业务逻辑。
- 列表场景看一帧里是否在主线程做解析、解码、锁等待。

练习：新增一个列表页（可以放在 `ui` 包下），`onBindViewHolder` 里对主线程 `Thread.sleep(32)` 或做一段可重复的重计算。抓滑动时的 System Trace。

过关：指出超标的 `doFrame`，并说出时间在 bind 而不是在 RenderThread。然后删掉 sleep，再抓一次，确认那些长 slice 消失。

辅助命令，用来量化，不代替看图：

```bash
adb shell dumpsys gfxinfo com.example.guo reset
# 滑动几秒
adb shell dumpsys gfxinfo com.example.guo framestats
```

看 janky frames / 百分位帧耗时，和 trace 里的长帧对上号。

调试期可以打开 StrictMode，把主线程磁盘和网络直接打成日志，避免等用户说卡了才发现：

```kotlin
StrictMode.setThreadPolicy(
    StrictMode.ThreadPolicy.Builder()
        .detectDiskReads()
        .detectDiskWrites()
        .detectNetwork()
        .penaltyLog()
        .build()
)
```

放在 debug 入口。StrictMode 负责「主线程上不该出现的 IO」，System Trace 负责「这一帧到底慢在哪」。

### 3. 第 3 周：内存

工具：Android Studio Memory Profiler。

顺序：

1. 操作前记一次堆大小。
2. 反复进入再退出目标页。
3. 手动 GC，看 Java 堆是否回到起点附近。回不去就抓 heap dump。
4. 在 dump 里从泄漏对象出发，沿引用链找到还握着它的那个字段（静态集合、单例、未注销的监听器、Handler、协程作用域最常见）。

练习：做一个页面，把 Activity 注册进一个静态 `MutableList`，退出不移除。重复开关 5 次，GC 后抓 dump，把引用链写下来。修好后再抓一次，确认实例数不再随开关次数上涨。

命令行对照：

```bash
adb shell dumpsys meminfo com.example.guo
```

分清 Java Heap、Native Heap、Graphics、Code。只涨 Java Heap 时继续用 heap dump；只涨 Native 时再学 Perfetto 的 heapprofd，这一周先不展开。

LeakCanary 放在这个练习做完之后接上。它自动化了「退出后仍可达」这件事，先手工走通引用链，才知道它报的链在说什么。

### 4. 第 4 周：启动

先拿数字，再抓 trace。

```bash
adb shell am force-stop com.example.guo
adb shell am start -W -n com.example.guo/.MainActivity
```

`TotalTime` 是这次启动的粗数。多跑几次取中位数。`ThisTime` / `WaitTime` 含义不同，比较优化前后时固定看同一个字段。

然后对冷启动抓 System Trace，从进程拉起到第一帧：

- `bindApplication`、`ActivityThread` 里主线程在跑什么。
- ContentProvider、Application 初始化、首页 onCreate 各占多久。
- 有没有主线程上的锁、磁盘、同步初始化 SDK。

练习：在 `Application` 或 `MainActivity.onCreate` 里加一段主线程 `sleep(500)`，对比 `am start -W` 和 trace。确认多出来的时间落在你加的那段，再删掉。

`onWindowFocusChanged` 可以作为「首帧已经画上」的观察点。真正要优化启动时，用 Jetpack Macrobenchmark 的 `StartupTimingMetric` 做可重复测量，这一周先把手工 trace 读懂。

### 5. 之后：让结论能回归

定位流程稳定之后再上这些，用来防止改完又慢回去：

- **Macrobenchmark**：滑动帧耗时、冷启动。结论写成测试，而不是只留一张截图。
- **Microbenchmark**：已经缩到一个函数时，量这个函数。它测不了掉帧和 ANR。
- **自定义 slice**：在嫌疑代码前后打 `Trace.beginSection("name")` / `Trace.endSection()`，或 `Trace.beginAsyncSection`。下次抓 System Trace 时，这段会直接出现在图上。名字用业务动作，例如 `parseHomeFeed`。
- **线上**：Debug 包用 StrictMode + 本地 trace。线上看 ANR rate、慢帧、冻结帧、慢启动。拿到的 ANR trace 仍按第 1 周的方法读：主线程栈、它在等的锁、持锁线程的栈。

Java/Kotlin Method Trace（Studio CPU 里的方法采样或插桩）的使用时机：System Trace 已经证明慢在本进程的 Java 代码，但 slice 太粗、看不到具体方法。插桩跟踪只圈短时间，因为它本身会把耗时放大。

Native 热点用 simpleperf，Native 内存用 heapprofd。出现 native 栈或 native 堆持续上涨再学，不提前铺开。

## 一张图要写出的结论

每次练习用这四行收尾，写在笔记里：

```
现象：
工具和操作：
结论：主线程在 ___ 花了 ___ ms，原因是 ___（对端线程 / 锁 / IO / 自身计算）
验证：改掉 ___ 后，同一路径的 ___ 从 ___ 降到 ___
```

写不出「对端是谁」时，继续在 trace 里点 owner，先别改代码。
